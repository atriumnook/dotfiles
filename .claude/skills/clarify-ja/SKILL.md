# Clarify（日本語）

レビューの基準は二つ。「この文章を読んだ第三者が、書き手に質問せずに同じ意味を理解できるか」と、「その箇所が、そこで読み手に伝えるべきことを伝えているか」である。AI らしい言い回しが問題になるのは、具体性が欠けて解釈を読み手に委ねるとき、書き手の判断が見えなくなるとき、または理解できても伝えるべきことからずれているときである。下のパターンは基準を満たさない箇所を見つけるための索引であり、パターンに一致していても、読み手が意味を復元でき、伝えるべきことを伝えている箇所は指摘しない。ただし文体の規則（9〜17）に当たり、読み手の負担になる箇所は「軽微」として別に挙げる。短文・対句・抽象語は、それだけでは問題にならない。

## 進め方

既定は review（指摘のみ）とし、書き換えを依頼されたときは rewrite を行う。入力がスライドや発表資料なら [slides.md](slides.md) の観点も当てる。

結果は 2 つに分けて示す。

- 指摘: 読み手が意味を復元できない箇所、または伝えるべきことを伝えていない箇所。原文の引用、規則番号、読み手が何を得られないか、修正案を示す。
- 軽微: 意味は復元できるが、文体の規則に当たり読み手の負担になる箇所。原文の引用、規則番号、修正案を一行で示す。軽微に入れるのは、要確認なしで修正案を出せるものに限る。要確認が必要なものは指摘に入れる。

意味を復元でき、読み手の負担にもならない箇所は、どちらにも挙げない。「深刻ではない」「参考までに」と添えたくなる細部も挙げない。

修正案で指示語の対象・主語・条件・数値・その箇所の目的を補うのは、本文か会話に根拠がある場合に限る。根拠なく補うと、書き手の意図と異なる具体的な誤りが生まれ、元の曖昧さよりも見つけにくくなるためである。根拠がない箇所は、書き手への質問として「要確認」に回す。

## 書き換えの手順

rewrite では、指摘と軽微の箇所それぞれに次の手順を当てる。言葉を削る前に、何を説明するかを組み立てる。

1. 伝えたいことを決める。その箇所で読み手に理解してほしいことを一文にする。仕組みを知る、違いを理解する、手順を実行するなど、文章の役割に合わせ、概念の説明に判断や行動の指示を足さない。本文と前後から決まらなければ要確認に回す。
2. 書き下す。文字数を気にせず、読み手が隣にいるつもりで、何がどうなるか、なぜそうなるか、どんな場合かを書く。「分離」「管理」「対応」「保証」などの語で実際の動作や条件を代用しない。本文と会話にない動作・効果・条件は書かない。「口頭で説明するつもりで」は内容を整理する方法であり、完成文の口調ではない。
3. 話題を分けて選ぶ。仕組み・利用条件・例外・注意点を別の文にし、条件はかかる文や表のセルの近くに置く。重複する補足や主題から外れる話の削除・移動は、7 点比較の 1 を変えるため、修正案ではなく構成の提案として示す。
4. 短くする。重複、前置き、回りくどい修飾を削り、主体・動作・因果関係・比較対象・条件は残す。公式用語は言い換えず、必要なら初出で意味を補う。言葉を削るだけで収まらなければ、話題を減らすか構成を見直す提案をし、略語や記号で詰めない。指定の長さでは条件を保てない場合は、圧縮せずに必要な長さを示す。
5. 短くした文だけで読む。書き下した文も原文も知らない読み手として、修正後の文を読み、レビューの基準を満たすか確かめる。隣の文と続けて読み、話題が急に変わらないか、用語が揺れていないか（規則 16）も見る。満たさなければ、語の置換を重ねず、手順 2 から組み立て直す。

書き下した文や検討過程は出力しない。

## 意味の保持

修正案は原文の意味を保つ。修正前後で次の 7 点を比べる。

1. 何について何を主張しているか
2. 何を認め、何を否定しているか（否定の言い回しではなく、否定された内容が情報として残っているか）
3. 誰が誰に何をするか
4. 条件と範囲
5. 数値・程度・強調（「重要」「必ず」など）・固有名詞・時期
6. 確度（断定・推量・伝聞）
7. 文の働き（事実・意見・依頼・仮定・比喩・引用）

修正案ごとに、比較の結果を一行添える（「7 点比較: 変化なし」、または変わった項目の番号）。比較を出力に書くことで、比較の省略を防ぐ。

一つでも変わる案は捨て、原文を残して要確認に回す。案を作り直して比較を通そうとはしない。言い換えを重ねるほど、比較を通る形のまま意味が少しずつずれていくためである。

修正後の文は日本語として自然でなければならない。補える箇所だけを直すと語の組み合わせが不自然になる場合（「片方」を「応答速度」に置き換えると「応答速度が崩れる」になる、など）は、本文か会話の根拠で足りる範囲で、文の組み立てから直す（書き換えの手順 2〜4）。根拠が足りなければ、文全体を原文のまま残し、まとめて要確認に回す。

rewrite では、修正後の全文、変更点の一覧、構成の提案、要確認の一覧を返す。ファイルへの反映を依頼された場合は、正本を編集し、ユーザーの既存の変更を保つ。

完了条件: 全文にすべての規則を当てている。各指摘に引用と規則番号がある。根拠なく補った語がない。どの修正案にも 7 点比較の結果があり、採用した案はどれも変わっていない。rewrite では、採用した修正文がどれも書き換えの手順 5 を満たしている。

## 修正例

元資料の例（説明用）。要確認でない行は文脈に根拠がある場合で、左の文だけでは右の語は決まらない。「開発速度」「保守性」「クォータ」などは、その文脈に書かれていて初めて使える。根拠がない場合は要確認の行のようになる。

| 修正前 | 修正後 |
|---|---|
| 片方だけを見て基準を作ると、もう片方が壊れます。 | 開発速度だけを基準にすると、保守性の要件を満たせなくなるおそれがあります。 |
| 判断に迷うものは、残さない側に倒します。 | 採否を判断できない項目は、原則として除外します。 |
| 依存構造は分割できない。動かしながら引き返す。 | 依存関係を分離できないため、稼働中のシステムを変更し、問題が発生した場合は元の状態に戻します。 |
| 受付と完了確認を分離する | 処理の終了を待たずに受付済みと返し、結果は後から問い合わせる |
| 上限数は到達保証ではない | クォータなどの制約により、表の台数まで増やせない場合がある |
| この対応は、運用負荷を大幅に下げる鍵となるでしょう。 | 原文のまま。要確認: 「この対応」が何を指すか、「大幅に」の数値、何がどう下がるか。 |
| Completed は、コードが最後まで実行された状態です。入力不正が0件であることを意味するわけではありません。 | 原文のまま。要確認（規則 18）: この箇所で読み手に伝えたいこと。たとえば入力不正の件数をどこで確認するかであれば、それを書く。 |

## パターン

番号は指摘で引用する固定 ID。

### 具体性

1. 結論が後ろにある。否定・対比・留保（「〜ではなく」「一見〜だが」）から始まり、伝えたい内容が後回しになっている。否定した側を消しても主張が変わらない場合だけ指摘する。「原因はキャッシュではなく DNS の設定だった」のように、消すと調査結果が失われる対比は対象外。
2. 主語・動作がない。誰が何をするかが読み取れない。名詞化（「〜の実施」「〜化を図る」）や受け身で行為者が消えている。「分離」「管理」「対応」「保証」などの語だけで、実際の動作や条件を代用している。
3. 指示語の対象が不明。「片方」「もう一方」「これ」「前者」などが何を指すか特定できない。
4. 抽象語。仕組み・前提・現場・価値・本質・解像度などが、実際にどの機能・条件・人を指すか分からない。読み手が必要とする公式用語・技術用語は抽象語ではないので、別の言葉に置き換えない。
5. 比喩的な動詞。倒す・壊れる・効く・刺さる・引き返すなどで、具体的な動作と結果が書かれていない。「効く」だけは、意味を復元できる場合も挙げる。結果が同じ文か前後に書かれていれば、「効く」を原因を示す表現に替え、結果はそのまま残す（「キャッシュが効いて、p95 が 120ms になった」→「キャッシュにより、p95 が 120ms になった」）。結果が書かれていなければ、何がどう変わるのか（「応答が速くなる」「〜を防げる」など）を要確認にする。
6. 条件と結果がない。発生条件、影響を受ける対象、結果のいずれかが欠けている。
7. 前提の省略。実行対象・判断基準・変更条件・復旧先など、主張や手順を理解するのに必要な情報が書かれていない。あれば親切だが、なくても主張を理解できる細部（日付の年、過去の経緯の詳細など）は対象外。
8. どの文書にも当てはまる文。別のプロジェクトの文書にそのまま載せられる文は、この文書について何も伝えていない。
18. その箇所の目的と合わない。見出し・前後・資料の目的から分かる、読み手がその箇所で知るべきことの代わりに、周辺の事実や「〜を意味するわけではない」という否定だけを述べている。文自体を理解できても指摘する。何を伝えるかは書き手が決めるので、前後から特定できる場合を除き、修正案を出さず要確認にする。
19. 異なる話の詰め込み。仕組み・利用条件・例外・注意点や、実行時間の制限と必要な設定のような別の話を一文につないでいる。または、条件がどの説明にかかるか分からない。

### 文体

9. 演出としての短文・対句・体言止め。区切ったことで、文同士の関係（理由・条件・順序）が失われている。
10. 強調の読点。「前提を、経路が添える」のように、文法上の必要がない位置で区切っている。
11. 三項目への当てはめ。内容に関係なく三つにまとめ、水増しや欠落が生じている。
12. 定型句。「〜と言えるでしょう」「〜が重要です」「鍵となる」「シームレスな」「〜を実現」「〜に寄与する」「結論から言うと」「いかがでしたか」など。具体的な事実を書けば不要になる。
13. 誇張とぼかし。「大幅に」「非常に」の代わりに数値を書けるのに書いていない。「〜の可能性があるかもしれない」のようにぼかしが重なっている。数値の根拠がない程度語は、削ると主張の強さが変わるので、削らずに要確認に回す。
14. 記号の多用。ダッシュやコロンで文をつなぐ。太字が多すぎて強調の意味がない。見出しや箇条書きに絵文字がある。「**性能:** 性能は〜」のように見出しを本文で繰り返す箇条書き。
15. 過度な圧縮。矢印・記号・略語の羅列や、「上限数は到達保証ではない」のような短いだけの独自表現で、読み手が文を復元しなければならない。
16. 同義語の言い換え。同じ概念を別の語で呼び、別物と誤読させる。
17. コピー調の体言止め。「自動更新できる、SSL サーバー証明書。」「用途で選ぶ、シンプルな 4 プラン。」のように修飾句と名詞を読点で区切って句点で止める形と、「〜の時代へ。」「〜の領域へ。」で止める形。意味を復元できる場合も挙げ、述語のある文（「SSL サーバー証明書を自動で更新できます。」）にする。スライドの見出しも対象。
