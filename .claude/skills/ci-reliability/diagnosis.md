# CI 失敗の診断

既存の確率的な失敗や CI の失敗を調べるときに、この手順を使う。依頼された read/write の範囲を守る。診断の依頼は、修正、パイプラインやワークフローの rerun、CI 設定の変更を含まない。

## 1. 証拠を凍結する

リポジトリ、パイプラインまたはワークフロー、job、コミット SHA、runner(名前・tag・ホスト)、時刻、失敗したテストやコマンド、最初に安定して現れる失敗のシグネチャを記録する。CI 基盤のメッセージとテストの出力は分けておく。大きなログは貼らず、run へのリンクを残す。各項目を埋めるか、取得できなかったことを記録したら、このステップは終わる。

取得の例(引数は各 CLI の `--help` で確かめる):

- GitHub Actions: `gh run list --commit <sha>`、`gh run view <run-id> --log-failed`、`gh api repos/<owner>/<repo>/actions/runs/<run-id>/jobs`(`runner_name` と時刻)
- GitLab: `glab api "projects/<id>/pipelines?sha=<sha>"`、`glab api projects/<id>/pipelines/<pipeline-id>/jobs`(`runner` と時刻)、`glab ci trace <job-id>`。JUnit の report を artifact に出していれば `glab api projects/<id>/pipelines/<pipeline-id>/test_report`

## 2. 失敗と成功を並べる(症例対照)

失敗した run と成功した run を、それぞれ複数集める。同じ SHA の run を優先し、それが無理なら、関係するテストと CI 設定が比較する commit 間で同一であることを確かめる。

因子ごとに表にする: SHA、runner とホスト、同時に走っていた job、matrix の軸(OS、版)、テストの実行順、cache の hit と miss、image の digest や toolchain の版、開始時刻。

失敗が偏る因子が owner の候補になる。失敗と成功を完全に分ける因子は強い手がかりである。どの因子にも偏らないときは、負荷依存の同期か順序依存を疑う。1 回の rerun の成功は基盤の障害を証明せず、1 回の timeout は製品の競合を証明しない。

## 3. 分類する

修正の内容からではなく、記録された証拠から分類する。

- **ホストリソースの衝突**: 同じポート、socket、データベース、予測可能なパス、cache、外部の namespace を、独立したプロセスや job が確保している。
- **不完全なライフサイクル**: 子プロセス、worker、stream、server、callback が quiescence に達する前に teardown が戻り、後の出力や変更が別のテストに現れる。
- **グローバル状態の汚染・順序依存**: 結果が、テストの順序や、漏れた環境変数・cwd・fake timer・global・mock・locale・module の状態に依存する。
- **負荷依存の同期**: sleep、polling の間隔、想定したイベントループの回数が、観測できる readiness や完了の代わりになっている。
- **非決定的な入力**: 結果が、固定していない乱数の seed、順序が保証されない集合の順序、現在時刻・タイムゾーン・日付の境界、浮動小数点の誤差に依存する。
- **環境のドリフト**: 同じ SHA でも、runner の image、固定していない依存や toolchain、浮動するタグ、外部の状態が変わると結果が変わる。通っていた時期と失敗し始めた時期の境目で、何の版が変わったかを証拠にする。
- **cache の陳腐化・汚染**: cache の hit と miss、または cache を作った job によって結果が変わる。cache を使わない run が通るかで確かめる。
- **リソース枯渇**: メモリ不足による kill(終了コード 137、oom-killer のログ)、ディスク不足(`ENOSPC`)、ファイルディスクリプタの枯渇。テスト自身のリークか、runner の容量不足かは、別々の事実として扱う。
- **プラットフォーム・実行経路の不一致**: 失敗が、OS、shell、ファイルシステムの規則、source と build のモード、実行エントリに一貫して従う。macOS で通っても、Windows のレーンについては何もわからない。
- **製品の並行性欠陥**: テストがリソースを制御しており、明示的に操作を重ねると決定的に再現し、出荷される振る舞いの競合を示している。
- **外部プロバイダの一時障害**: 失敗が live API やネットワークの境界に属し、文書化された retry の方針に合う。
- **runner 基盤**: checkout、依存のダウンロード、ディスク、ホストのプロセス、runner のサービスが、テストのコマンドとは独立に失敗する。この分類には runner 側の直接の証拠が要る。ホストのメトリクスが見られない self-hosted の pool では、その旨を書き、ログにある事実から分類する。無関係なブランチで同じシグネチャが同じ pool に繰り返し現れるなら、ホストを調べられなくても、共有ホストでの競合の証拠になる。

証拠が独立した複数の事実を示すなら、それぞれを報告する。timeout、signal、終了コード、assertion は、1 つの推測にまとめず別々に書く。

## 4. 最小のトポロジーで再現する

失敗したテストファイルや、絞ったテスト名から始める。シグネチャを再現する最初の段まで、同時実行の度合いを上げていく。

1. 単一のテストプロセス
2. 実行順の shuffle(例: pytest-randomly、`go test -shuffle=on`、`vitest --sequence.shuffle`、`jest --randomize`)
3. 同時に走るテストやファイル
4. 独立した複数のテストプロセス
5. CI と同じ image・環境変数・worker 数・source と build のモード
6. 同じホストのリソースを共有する別の job や runner(CI そのもの)

再現は、CI と同じ設定・環境変数・プラットフォームで行い、本番の timeout や負荷の条件はそのまま使う。条件を変えて作った失敗は、元のシグネチャとは別のものになる。

- 順序依存が疑わしいなら、失敗するテストの前に走るテストの集合を二分探索で絞り、状態を汚しているテストを特定する。
- 競合が疑わしいなら、確率的なタイミングを、争点の遷移に置いた barrier で置き換える。
- ホストのリソースの衝突が疑わしいなら、同じ識別子が同時に確保されたことを示すか、atomic で一意な確保が衝突を消すことを示す。

手元で走らせられないプラットフォームのシグネチャなら、はしごは届く最後の段で止まる。その限界を記録し、別のプラットフォームでの成功で代用しない。CI を再現の手段にするときは承認を得たうえで、1 回の run で変える疑わしい owner を 1 つにし、結果をその owner に帰着できるようにする。

## 5. owner で直す

実装が許可されているときは、リソースを確保する、readiness を公開する、グローバル状態を変える、teardown を担うコンポーネントを直す。snapshot の正規化、retry の wrapper、広げた timeout、全体の逐次化、弱めた assertion は失敗を隠すだけである(SKILL.md の「masking と quarantine を区別する」)。環境のドリフトや cache の陳腐化では、版の固定や cache key の修正(SKILL.md の「入力を固定する」)が owner での修正になる。

安定した fixture のデータと、実行時のリソースの確保は分ける。記録した URL は安定したまま残し、fixture がその通信先を OS が割り当てたポートに対応づける。安定した期待値のパスは assertion のまま残し、共有の書き込み先にはしない。

## 6. 調査を閉じる

次をすべて満たしたとき、証拠が揃ったと言える。

- 元のシグネチャに、証拠に支えられた分類がある。
- 最小のトポロジーで再現したか、外部の証拠が十分で、再現できなかった限界を明記している。
- 許可された修正が、negative control か修正前の状態で失敗し、同じトポロジーで修正後に通る。
- owner に応じて求められる証拠(独立プロセスの同時実行、復元、quiescence までの teardown、繰り返し実行の p0 と n)が揃っている。
- 残る CI のチェックを、観測した状態(成功・pending・skip・失敗)のまま報告している。

選んだ証拠で結論が立ったら止める。結論が立たないときは、分類を阻んでいる欠けた事実を報告する。
