# CI の信頼性

CI の失敗は、共有された環境で起きた事実の記録として扱う。目的は、失敗を原因の owner(リソースを確保する、readiness を公開する、グローバル状態を変える、teardown を担う箇所)に帰着させ、そこで直すこと。手元で単独実行したときではなく、CI の実際のトポロジーで正しく動くテストと設定を作る。

既存の失敗を調べるときは [diagnosis.md](diagnosis.md) の手順に従う。診断だけを頼まれたときは read-only のまま、原因と証拠を報告する。

## トポロジーを想定する

設定で否定されない限り、次の層は同時に走りうると想定する。

1. 1 つのテストファイル内のテスト
2. 別のファイルや worker プロセス
3. 1 つのジョブ内の、独立したテストプロセスやコマンド
4. 同じホストを共有する別ジョブ(並列 job、matrix、self-hosted runner で同時に走る job)

プロセスを分けても、ホストのポート、予測可能なファイルパス、外部サービス、データベース、socket、引き継いだ子プロセス、runner 上の cache や作業ディレクトリは分離されない。確保するリソースごとに、owner、atomic な確保の手段、観測できる readiness の合図、登録済みの cleanup、quiescence の合図を特定する。

隔離が足りない fixture が 1 つあるときは、その排他範囲を狭めるか、確保の方法を変える。テストファイル内の逐次実行は、別のファイル・プロセス・ジョブ・runner からホストのリソースを守らない。

## リソースを atomic に確保する

空きを確かめてから後で確保するのではなく、リソースの owner が持つ割り当ての仕組みを使う。

- ネットワークの fixture は loopback に port 0 で bind し、listen 完了の通知を受けてから、割り当てられたアドレスを読む。
- 一時ディレクトリは、テストごとに `mkdtemp` 相当で作る。
- 共有のデータベース、socket、セッション、出力先には、テストごとに一意の namespace を与える。
- 存在してはならないパスは、排他的作成(`O_EXCL` 相当)で作る。
- 記録済みの安定した識別子(snapshot 中の URL など)と、実行時の一時的なアドレスは分け、fixture の中で対応づける。

parser の入力や期待値として使うだけのリテラルのパスや URL は、確保されるリソースではないので、そのまま残す。

## グローバル状態を封じ込める

環境変数、cwd、fake timer、locale とタイムゾーン、module の mock、registry や singleton、console の hook、グローバルな HTTP の傍受は、排他的に使う可変リソースとして扱う。

まず依存の注入やインスタンス単位の adapter を使う。変更が必要なときは次のようにする。

- 元の値が「なかった」のか「あった」のかを記録し、その状態に正確に戻す。
- 変更の直後に復元を登録する。
- 変更する範囲を最小にして try/finally で囲む。局所の finally に届く前に失敗しうるなら、afterEach 相当の後始末も残す。
- fixture が担う、正確なリクエストや呼び出しだけを傍受する。

## 入力を固定する(hermetic)

同じコミットは、いつどこで実行しても同じ結果になるようにする。結果を左右する入力は、すべて固定するか、テストが明示的に与える。

テストの側:

- 乱数は seed を固定するか、実行ごとの seed を失敗時に出力して再現できるようにする。
- 現在時刻・タイムゾーン・locale は注入するか固定する。日付の境界(月末、年末、DST の切り替え)が仕様に関わるなら、その時刻を与えるテストを書く。
- 順序が仕様でないもの(hash の iteration、ファイルシステムの列挙、並行処理の完了順)は、順序を問わない比較で検証する。順序が仕様なら、順序そのものを検証する。
- 浮動小数点は、仕様の許容誤差で比較する。

CI の側:

- toolchain、依存、コンテナ image、CI の action や template は版を固定する(lockfile、digest、コミット SHA)。浮動するタグは、同じコミットの結果を時間とともに変える。
- cache は速さにだけ効くようにする。cache key には結果に影響する入力(lockfile のハッシュ、toolchain の版、OS)をすべて含め、cache がなくても同じ結果になる状態を保つ。
- 前の job の作業ディレクトリや成果物が残る設定(GitLab の shell executor と `GIT_STRATEGY: fetch` など)では、job が必要とする状態を毎回作り直す。

## プラットフォームが決める意味に従う

同じテストが Windows と POSIX で走るとき、OS が持つ値は、書いたとおりに戻ってくるとは限らない。

- 書き戻した値に依存する assertion は、書き戻しが失われないことを前提にしている。NTFS のタイムスタンプは 100 ナノ秒単位なので、ミリ秒未満の端数は戻らないことがある。期待値は、記憶した値ではなく、書き戻した後に読み直した値から取る。
- Windows は環境変数名の大文字と小文字を区別しない。`http_proxy` と `HTTP_PROXY` は 1 つの項目になる。
- Windows はファイルハンドルを非同期に解放する。rename や削除には、観測した競合に見合う上限付きの retry を付ける。
- Windows には POSIX の permission や signal の意味がない。それに依存するテストは、理由を書いたプラットフォーム指定の skip にする。

全プラットフォームで成り立つ観測を選び、どうしても成り立たない場合は、そのプラットフォームを明示的に除外する。

## 時間予算をレーンに合わせる

個別のテストや suite に指定した timeout は、runner 全体の timeout を上書きする。それより小さい値は、CI が与えた予算を削る。プロセスの起動に律速される suite はレーンの予算をそのまま使い、より厳しい値には理由を添える。

テストの予算を上げるときは、setup と teardown の hook の予算も上げる。hook も同じ競合を受けるので、テストだけを上げると失敗が teardown に移る。

timeout そのものを検証するテストでは、外側の待ち時間を、検証対象の timeout より十分大きくとる。20 ms の deadline が発火することを示すテストが、テスト基盤自身の待ち時間と競争しないようにする。

## 状態で同期する

固定の sleep は、setup の完了や cleanup の収束の証拠にならない。

- 明示的な readiness のイベント、ハンドシェイク、状態遷移、owner が持つ promise、外部から観測できる条件を待つ。
- 競合を検証するときは、deferred promise や barrier で競合を決まった地点に置き、操作が重なったことを示す。
- timeout は待ちの上限にだけ使う。assertion を正しくする条件は、観測した状態にする。
- スケジューラに依存する順序は、その順序が製品の仕様であるときだけ検証する。
- 時間そのものが検証対象なら、clock を注入するか fake にし、必ず実時間に戻す。

## quiescence まで dispose する

確保した直後に cleanup を登録し、assertion が失敗してもリソースが解放されるようにする。cleanup では、新しい callback やリクエストを止め、listener を外し、グローバルな hook を戻し、owner が持つ処理を終わらせ、子プロセスの終了・server の close・worker の終了などの完了の合図を待つ。

`abort()`・`close()`・`kill()` を呼んでも、完了の合図を待つまで teardown は終わっていない。遅れて完了する処理がありうるなら、dispose の後にそれが別のテストの状態を変えられないことを示す。

## masking と quarantine を区別する

修正は、失敗の原因の owner を変えるものに限る。次は失敗を見えなくするだけの masking なので、根本修正として示さない。

- 待っている状態を特定しないまま timeout を延ばす。
- テストやジョブに retry を足す(テストランナーの rerun 機能、GitLab の `retry` で `when` が `script_failure` や `always` のもの)。
- すべてを逐次実行にする。
- エラーや unhandled rejection を握りつぶす。
- assertion を弱める。不安定な挙動を正規化して消す。
- cleanup や assertion の前に sleep を足す。
- 失敗を許容する設定(GitLab の `allow_failure`、GitHub Actions の `continue-on-error`)で失敗を消す。

次は masking ではない。

- 外部の境界に限った retry。runner 基盤の失敗(GitLab の `retry:when` の `runner_system_failure`・`stuck_or_timeout_failure` など)や、retry の方針が文書化された外部 API に対するもの。
- 予算を元に戻すこと。suite を、レーンがもともと与えていた予算に戻すことや、runner で実測した競合に合わせて上限付きの retry を決めることは、待っている処理を特定している。

quarantine(テストの一時隔離)は修正ではなく、記録された延期である。次をすべて満たすときだけ quarantine として扱う。

- skip や失敗許容の設定に、理由と issue へのリンクを書いている。
- owner と期限が決まっており、期限が来たら修正して戻すか、テストを削除する。
- 対象が、セキュリティやデータの整合性を守るテストではない。

報告では「隔離した」と書き、「直した」とは書かない。quarantine は CI 設定やテストの変更なので、依頼範囲に含まれない限り提案にとどめる。

## 修正を証明する

- 修正前に、通常の回帰が失敗することを実行して確かめる。
- 新しい静的チェックやガードは、拒否すべきケースを一時的に入れ、意図どおり失敗することを確かめる(negative control)。
- 競合は barrier で操作の重なりを示す。繰り返し実行だけでは競合のテストにならない。
- ポート、socket、共有パス、subprocess などホストのリソースに関わる修正で、プロセス間の隔離が修正の一部なら、独立したテストプロセスを同時に走らせて確かめる。
- 自前の deadline を持つ子プロセスを起動する fixture では、終了コードを検証する前に、signal や timeout で終わっていないことを確かめる。kill された子プロセスが、終了コードの不一致ではなく timeout として報告されるようにするため。
- component の自己申告ではなく、外部の状態、イベント、ファイル、ログ、終了、dispose を確かめる。

決定的な回帰テストを置いたうえで、なお確率的な失敗が残りうるときは、繰り返し実行の回数を統計で決める。

- 修正前に、再現したトポロジーで失敗率 p0 を測る。
- 修正後に n 回連続で成功したとき、失敗率が p0 のままである確率は (1−p0)^n である。これを 5% 以下にするには n ≥ ln(0.05) / ln(1−p0) 回が要る。

  | p0 | 必要な連続成功回数 |
  |---|---|
  | 10% | 29 |
  | 5% | 59 |
  | 2% | 149 |
  | 1% | 299 |

- p0 を測れていないときは「直した」と主張せず、n 回連続成功から言える上限(95% の信頼度で失敗率は約 3/n 以下。rule of three)を報告する。
- 繰り返し実行は、ローカルの再現トポロジーで行う。CI での rerun は共有の runner の枠を消費し、デプロイなどの副作用を起こしうるので、実行前に承認を得る。

## 報告する

影響を受ける振る舞いに絞った、最小の回帰テストを実行する。変更がそのリスクを担うときだけ、トポロジー固有の証拠を加える。

- グローバル状態の変更には、復元の証拠
- ライフサイクルや subprocess には、quiescence まで teardown した証拠
- ポート、socket、共有パスには、独立プロセスを同時に走らせた証拠
- 新しいガードには、negative control
- 繰り返し実行による主張には、p0・n・結果

実行したコマンドと観測した結果をそのまま報告する。retry で通ったもの、skip したもの、pending の CI は、その状態のまま書く。
